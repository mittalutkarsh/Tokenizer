3 · Load programmatically

import json, unicodedata

vocab  = json.load(open("tokenizer/vocab.json"))
inv    = {v: k for k, v in vocab.items()}
merges = [tuple(l.split())
          for l in open("tokenizer/merges.txt")]

def tokenize(text, merges, inv, vocab):
    rank = {p: i for i, p in enumerate(merges)}
    out  = []
    for w in text.split():
        ids = list(w)
        while len(ids) >= 2:
            best = min(
              range(len(ids)-1),
              key=lambda i: rank.get(
                (ids[i], ids[i+1]),
                len(rank)))
            if (ids[best],ids[best+1]) not in rank:
                break
            ids[best:best+2] = \
              [ids[best]+ids[best+1]]
        out.extend(ids)
    return out

tokens = tokenize("India", merges, inv, vocab)
print(tokens)  # ['India']
⚙️ BPE Implementation: v1 (String / Regex) vs v2 (Integer-ID + Deque)

v1 — String / Regex approach (first implementation)

Words stored as space-joined character strings. Merging uses re.sub() with lookbehind/lookahead anchors to avoid partial matches. 

# word representation
"hello" → "h e l l o"

# pair count
symbols = word.split()
for i in range(len(symbols)-1):
    pairs[(symbols[i], symbols[i+1])] += freq

# merge — regex with boundary anchors
bigram  = re.escape(" ".join(pair))
pattern = re.compile(
    r"(?<!\S)" + bigram + r"(?!\S)")
new_word = pattern.sub("".join(pair), word)
  • String split on every pair-count step
  • Regex compile + sub per merge per word
  • Full corpus re-scanned each iteration
  • Tie-break: lexicographic max of string repr

v2 — Integer-ID + Deque (current, from BPETokenizerSimple)

Words stored as tuples of integer token IDs. Pair counting zips adjacent integers. Merging uses a linear deque scan — no regex overhead. Based on the BPETokenizerSimple class provided, with word-frequency dict deduplication added. 

# word representation
"hello" → (12, 17, 21, 21, 24)  # int IDs

# pair count — zip is O(n), ints compare fast
for id_a, id_b in zip(ids, ids[1:]):
    pairs[(id_a, id_b)] += freq

# merge — deque, no regex
dq = deque(ids)
while dq:
    cur = dq.popleft()
    if cur == a and dq and dq[0] == b:
        result.append(new_id)
        dq.popleft()       # skip b
    else:
        result.append(cur)
  • Integer equality = single CPU instruction
  • No regex compile/exec per merge step
  • Word-freq dict: 2 MB corpus → 12,710 unique types
  • Fast-skip: if a not in ids: continue
  • Tie-break: prefer lower IDs (ASCII-first → English edge)

Delta: what changed from v1 → v2 and why

Dimension v1 v2 Why it matters
Word storage "h e l l o" string (12,17,21,21,24) int tuple Integer equality is O(1); string equality is O(len). ~3–5× faster pair counting.
Merge engine re.compile + re.sub Linear deque scan Eliminates regex compilation (one per merge step) and lookbehind overhead.
Corpus dedup Full text repeated Word-frequency dict Collapses 2 MB weighted corpus to 12,710 unique word types. Each merge step is 100–200× smaller.
Fast-skip No skip — scan all words if a not in ids: skip After early merges, most words don't contain the target pair. Skipping them is a major speedup.
Tie-breaking Lex-max of string repr (Telugu chars win ties — higher Unicode) Lower token ID wins (ASCII/English wins ties) Telugu chars are U+0C00+, ASCII is U+0020–007E. v1 inadvertently gave Telugu a tie-break advantage; v2 flips this to help English stay under the fertility constraint.
🎛️ Trainable Parameters & Training Decisions

Per-language corpus weights

Each language's article is repeated weight times so BPE learns proportionally more merges for that script. The weights are the primary tuning knob.

English
115  (20.5%)
Hindi
80   (14.3%)
Telugu
230  (41.1%)
Tamil
130  (23.2%)

Telugu gets 41% of the budget despite being the shortest article (20 KB vs 65 KB English) because Telugu script has the richest unique character combinations — it needs the most dedicated BPE merge slots to achieve competitive fertility.

Vocabulary pre-seeding (20 free merges)

Before the BPE training loop starts, fixed high-frequency bigrams are injected directly into the vocabulary and pre-applied to the word-frequency dict. These are "free" merges — they don't compete with other languages for budget.

English pre-seeds (10, hardcoded):

th   he   in   er   re   on   an   en   at   or

Telugu pre-seeds (10, computed at runtime from article text):

్ర   ార   ాల   లు   ర్   లో   స్   ్య   భా   రా

These 20 pre-seeds each occupy 1 vocab slot (out of 10,000). The remaining 9,678 slots are filled by the BPE training loop. Pre-seeding was critical for English to cross the ≤ 1.6 fertility constraint without triggering the merge cascade that occurs when English weight crosses the 115/230 ratio threshold.

All other training decisions

  • Unicode NFC normalization — applied to all texts before training. Ensures precomposed and decomposed forms of the same character are treated identically (e.g. ā precomposed = a + combining macron).
  • Plain whitespace pre-tokenization — words split on whitespace only; merges apply strictly within each word. Chosen over GPT-2's Ġ-prefix style because (a) it aligns token boundaries with the fertility definition, and (b) Ġ would add extra prefix characters to every word, consuming merge budget unnecessarily.
  • Min-frequency = 1 — all word types retained. With language weights ≥ 80, even a word seen once in the raw article has effective frequency ≥ 80, so frequency filtering at 2 would drop nothing useful.
  • Special tokens — [UNK], [CLS], [SEP], [PAD], [MASK] occupy IDs 0–4 and count toward the 10,000 vocab budget (5 slots).
  • Initial character vocabulary — 302 unique characters across all four scripts plus special tokens, sorted by Unicode code point and assigned sequential IDs.
  • Exact vocab size = 10,000 enforced by assertion: 302 chars + 5 specials + 10 En pre-seeds + 10 Te pre-seeds + 9,673 BPE merges = 10,000.
  • Tie-breaking — on equal pair frequency, the pair with the lower sum of token IDs wins. Since ASCII characters have lower Unicode values → lower IDs, English-script pairs win ties, giving English a marginal merge-budget edge without changing the algorithm.

Ours (domain-specific)

With every one of 10,000 vocab slots targeted at exactly these four scripts and corpus weights tuned to balance fertility, we achieve score 6,154 — 14× better than BERT-multilingual and 73× better than GPT-4 on this language mix, using 12× fewer vocab entries than BERT.

Key takeaway: General-purpose tokenizers trade per-language efficiency for breadth. A domain-specific tokenizer trained on the exact language mix and domain (4 Indian languages, Wikipedia) dramatically outperforms industry models on the fertility gap metric — even with a fraction of their vocabulary budget. The industry tokenizer that comes closest (BERT-multilingual) still has a gap of 2.29 vs our 0.163.
📈 Tuning History & the Cliff Effect

Key configurations explored during optimisation. The most striking finding is the "cliff effect": a difference of just 1 unit in the English weight (110 → 120 out of 230 Telugu) caused English fertility to drop from 1.60 to 1.39 while Telugu jumped from 1.48 to 1.90. This is because BPE is a greedy algorithm — once a critical English character pair crosses the frequency threshold, it cascades: that merge enables downstream merges, all firing in the same training run.
